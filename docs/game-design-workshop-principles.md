# Game Design Workshop Principles For This Project

This document converts playcentric design into practical design rules for this project. It is not a book summary. Use it as a decision guide when designing or modifying chapters, planets, black boxes, the ship hub, or motherworld buildings.

## 1. 本项目的游戏类型

本项目不是传统 RPG，不是答题游戏，也不是纯工具平台。

本项目定位为：

**AI 文明探索冒险 / AI literacy adventure through creation and restoration**

核心体验是：

探索星球 -> 发现文明问题 -> 学会一种 AI 能力 -> 用自己的话证明理解 -> 点亮星球 -> 回母星创造作品。

玩家不是在刷题，也不是在使用一组功能菜单。玩家是在一个失序的 AI 文明宇宙里，通过观察、选择、表达和创作，修复星球、回收知识、建设母星。

## 2. 玩家体验目标

每个关卡设计前，必须先写清楚体验目标，而不是先写功能列表。

必须回答：

- 孩子应该感到什么？
- 家长应该看到什么价值？
- 这个关卡训练哪种 AI 素养？
- 这个关卡的情绪高潮是什么？

示例：第二章目标

- 孩子感到自己在修复一颗沉睡的信息星球。
- 家长看到孩子在练习表达、判断和验证。
- 学习重点是语言模型的使用边界。
- 高潮是黑匣开启与星球复苏。

如果一个设计不能说清楚孩子的感受、家长看到的价值、训练的 AI 素养和情绪高潮，就不应进入实现阶段。

## 3. 核心循环

本项目的核心循环是：

观察场景
-> 主动探索
-> 触发文明机关
-> 完成低压力互动
-> 获得文明碎片
-> 点亮地标
-> 解锁黑匣
-> 用自己的话完成理解输出
-> 星球复苏
-> 回母星创造作品

这个循环应优先于普通任务流、菜单流或表单流。新增内容时，应尽量让玩家经历“看见变化、参与修复、留下成果”的过程。

## 4. 玩法设计原则

每个玩法必须满足以下原则：

1. 不做纯阅读知识卡。知识应通过场景、机关、碎片、反馈或作品任务出现。
2. 不做普通选择题堆叠。选择题可以作为轻互动的一部分，但不能成为主要玩法形态。
3. 不让孩子一上来面对空白输入框。先给场景、例子、可选线索或半成品表达。
4. 先观察，再选择，再半开放表达。表达任务应建立在前面的观察和选择之上。
5. 反馈必须优先表现为世界变化。正确理解应带来点亮、复苏、路径打开、黑匣升温、建筑响应等变化。
6. 奖励不只是数值，而是点亮、解锁、复苏、收藏。科技点和资源可以存在，但不能替代可感知的世界反馈。
7. 玩法必须和场景功能有关。档案塔训练归档和证据，信件港训练缺失信息，母星建筑训练作品沉淀。

避免把 AI 素养训练写成“知识说明 -> 答题 -> 下一页”。更好的结构是“异常场景 -> 玩家处理 -> 世界响应 -> 规则被孩子说出来”。

## 5. 场景设计原则

场景不是背景装饰，而是引导玩家行动的系统。

场景设计要求：

- 用光、路径、建筑轮廓、动效引导点击。
- 少用大段任务文字。
- 地图上只显示必要提示。
- 详细内容点击后再出现。
- 不把功能堆成菜单。

玩家应该先从画面里感到“这里有东西需要我靠近”，再通过点击看到解释和任务。界面文字负责确认和收束，不负责替代探索。

对于星球、主舰和母星，优先使用空间关系表达功能：哪里是入口、哪里被封存、哪里已点亮、哪里等待资源。不要把这些内容简单压成按钮列表。

## 6. 母星设计原则

母星不是功能列表页。

母星是孩子的 AI 创造基地。

母星设计原则：

- 建筑分布在地图上。
- 建筑逐步解锁、逐步点亮。
- 外部星球获得的资源回流到母星。
- 母星功能必须产生作品或成果。
- 家长能在文明展厅看到孩子的成长证据。

母星的价值不是“有很多入口”，而是让孩子看到自己已经创造过什么、学会过什么、还能把这些能力用来做什么。

母星建筑应承担明确的作品方向：

- 文明展厅：展示成果、船员、星球、黑匣和课堂证据。
- 星球工坊：整理和建设母星。
- 作品委托所：把 AI 素养变成短创作任务。
- 角色对话室：练习提问、边界和复盘。
- 动画片工作室：把故事整理成三幕分镜。
- 文明档案馆：沉淀 AI 使用原则。
- 船员宿舍：保存伙伴关系和远征记录。
- 探险计划室：写目标、风险和复盘计划。

如果一个母星功能不能产生作品、记录、卡片、分镜、档案或可展示成果，它不应优先实现。

## 7. 关卡设计检查表

每新增一个关卡，必须回答：

- 玩家动词是什么？
- 玩家要做出什么选择？
- 是否有低压力引导？
- 是否有清楚反馈？
- 是否让世界发生变化？
- 是否能保存为成果？
- 是否能让家长理解价值？

建议把答案写在关卡设计说明或 PR 描述里。若这些问题只能用“阅读”“点击下一步”“填写表单”回答，说明设计还没有转化成适合本项目的游戏体验。

## 8. Playtest 问题

每次线下试玩后记录：

- 孩子最先点了哪里？
- 哪一步卡住了？
- 哪个动画最有感觉？
- 哪个任务像答题？
- 孩子是否理解自己为什么要做这件事？
- 家长是否能看懂孩子学到了什么？
- 孩子是否愿意继续探索母星或下一颗星球？

试玩记录优先用于判断体验是否清楚，而不是证明设计者的解释是否正确。如果孩子没有从画面和反馈里理解任务，就应调整场景引导、交互顺序或反馈表现。

## 9. 后续开发约束

以后 Codex 在修改关卡、母星、黑匣、建筑玩法时，必须优先遵守本文件。

如果新增功能只是信息卡片、菜单入口或普通表单，而没有探索、反馈、点亮、作品沉淀，就不应优先实现。

开发时优先问：

- 这个功能是否属于 AI 文明探索冒险？
- 玩家是否先观察，再行动，再表达？
- 成功反馈是否改变了世界？
- 结果是否能回到主舰或母星成为成果？
- 家长是否能一眼看出孩子练习了什么？

本项目的增长方向应是更强的探索感、更清楚的 AI 素养训练、更可见的世界变化和更完整的作品沉淀，而不是更多菜单、更多说明页或更多孤立表单。
